# Изменения

## 2026-08-28 — потолок на время ответа

С жалобы «на „ау" бот отвечал 500 секунд». Дело оказалось не в скорости модели:
**у машинерии повторов не было потолка по времени**. Замер на заглушке, которая
таймаутит, показал девять последовательных обращений — три попытки на каждую из
трёх моделей (текущая + две запасные). При штатных таймаутах это ~1022с для
ответа и ~2045с для маршрутного вызова. Пятьсот секунд укладывались внутрь.

Общего потолка на обработку сообщения не было вообще: ни `asyncio.wait_for`
вокруг цикла поиска, ни дедлайна на попытки.

Появились четыре бюджета, все настраиваются переменными окружения:

- `TOTAL_DEADLINE` (180с) — на **все** попытки одного запроса. Таймаут каждой
  попытки дополнительно урезается остатком бюджета, иначе последняя перепрыгнула
  бы дедлайн. Пауза между повторами тоже тратит бюджет — без этой проверки
  шестисекундное ожидание вылезало за потолок (поймано тестом).
- `STREAM_TIMEOUT` (150с) — одна попытка стриминга. Прежние 60с ставились под
  модель, отдававшую первый токен за 1.3с; рассуждающая молчит, пока думает, и
  живая попытка «протухала» впустую.
- `ROUTE_TIMEOUT` (60с) — вызов «нужен ли поиск». Он необязательный: не успел —
  отвечаем без поиска.
- `RESEARCH_BUDGET` (240с) — весь цикл поиска, до шести кругов.

Теперь пользователь гарантированно получает ответ или честную ошибку, а не
молчание в чат. В логи пишется длительность этапа поиска и всей обработки —
следующий медленный случай будет видно в Railway без догадок.

«Ау», «алло», «эй», «работаешь» и родня добавлены в `SMALL_TALK`, так что
маршрутный вызов на них не тратится.

## 2026-08-28 — скорость ответа на простые реплики

После перехода на рассуждающую модель простое «привет» стало ждать заметно
дольше. Причин оказалось две, и обе измеримы.

**Шаг веб-поиска стоит отдельного обращения к модели.** Прежде чем писать ответ,
бот отдельным вызовом спрашивает модель «нужен ли интернет». У рассуждающей
модели это решение само по себе стоит полного прохода размышлений, то есть
«привет» оплачивалось дважды. Трассировка обработки сообщения показывала два
вызова там, где хватает одного. Теперь приветствия, благодарности и прочая
болтовня уходят сразу в ответ, минуя этот шаг. Совпадение считается только
целиком: «привет, найди курс биткоина» по-прежнему идёт через поиск, и решает
там модель, а не список слов.

**Сила рассуждений была максимальной везде.** Muse Glimmer читает её из
системного промпта (`Reasoning strength: low|medium|high|xhigh`), по умолчанию
`high`. Маршрутный вызов решает единственный бинарный вопрос — думать там нечего.
Теперь на маршрут уходит `low`, на ответ `medium`; настраивается переменными
`ROUTE_REASONING` и `ANSWER_REASONING`. Моделей, которые эту строку не понимают,
изменение не касается — лишний `system` им не отправляется.

На синтетической трассировке с шестисекундным проходом размышлений «привет»
сократился с 12.1с до 6.0с. Реальные цифры зависят от нагрузки эндпоинта.

### Попутно найденный баг

`_is_interview_active` был объявлен `async`, но вызывался без `await` — в `if`
попадала корутина, а она всегда истинна. Перехватчик техсобеседования из-за
этого срабатывал на **каждом** сообщении, и слова «стоп», «дальше», «объясни»
уходили в собеседование, которого никто не начинал. Функция ничего не ждёт,
поэтому стала обычной.

### Осталось

Пока идёт маршрутный вызов, таймер в сообщении стоит на «Думаю… ⏱ 0с»: задача
таймера стартует только после блока поиска. На приветствиях это больше не видно
(шаг пропускается), на остальных вопросах — видно.

## 2026-08-28 — разбор кодовой базы и починка

Модель по умолчанию сменилась на `meta/muse-glimmer-30b` (Muse Glimmer 30B от
Meta, хостится на NVIDIA API). Немотроны остались в `/menu` и работают как
запасные модели. **Сохранённый в `progress.json` выбор модели важнее нового
дефолта** — если бот продолжает отвечать прежней моделью, переключитесь через
`/menu` или удалите ключ `"model"` из `progress.json`.

### Сломанное, что теперь работает

- **`/quiz`, `/poll`, `/code`, `/task`.** Команды были зарегистрированы через
  лямбду, передававшую хендлеру лишний третий аргумент, и падали с `TypeError`
  ещё до первой строки тела. У `/task` вдобавок не существовало самого
  `task_handler` — `NameError`. Кнопки в меню работали, потому что зовут
  `_run_quiz`/`_run_task` напрямую, поэтому баг и не был заметен.
- **Код в ответах.** Чистка HTML-тегов шла по сырому тексту и съедала угловые
  скобки внутри блоков кода (`std::vector<int>` → `std::vector`), а финальная
  сборка переносов срезала отступы — любой Python приезжал одной плоской
  лестницей. Теперь блоки кода прячутся до чистки и до схлопывания переносов.
  Заодно перестали ломаться `` `vector<int>` `` в строке и `# комментарий`
  внутри ` ```bash `, который уезжал в заголовок.
- **Оценка письменного ответа на `/interview`.** `_extract_grade` возвращал
  `None`, когда модель не написала «X/10», а вызывающий код сравнивал результат
  с числом — `TypeError`, и вместо разбора приходило «Не удалось оценить ответ».
  Балл без оценки больше не тянет средний вниз, будто кандидат ответил на ноль.
- **Чужие сессии собеседования.** Завершение сессии делало
  `INTERVIEW_QUIZ.clear()` и гасило маппинг поллов для всех чатов сразу.
- **Приветствие новых участников.** `member.id == BOT_USERNAME` сравнивал `int`
  со `str` и всегда давал `False` — бот здоровался сам с собой.
- **Расписание в GitHub Actions.** Шаг `uses: railway/cli@v3` ссылался на
  несуществующий репозиторий (настоящий CLI — `railwayapp/cli`), поэтому workflow
  падал на резолве экшена и бот никогда не стартовал и не останавливался по
  расписанию. Переписано на `npm install -g @railway/cli`; `railway down` получил
  `--yes`, иначе CLI ждёт подтверждения; ручной запуск через `workflow_dispatch`
  теперь спрашивает start/stop.
- **Остановка бота.** `loop.run_until_complete(app.run_polling())` — в PTB 21
  `run_polling` синхронный и сам управляет циклом; при остановке в
  `run_until_complete` прилетал `None` и всё падало.

### Ресурсы и состояние

- Двенадцать мест создавали свой `Bot(token=...)` на каждое действие — у каждого
  свой пул httpx-соединений, который никто не закрывал. Теперь один общий
  экземпляр из `Application`.
- Чтение настроек (а оно идёт на каждое сообщение) заводило запись в
  `USER_CONFIG`, и `progress.json` пух от чатов, которые ничего не настраивали.
  Для чтения появился `_peek_user_settings`, записи он не создаёт.
- `CONVERSATION_HISTORY` и `CHAT_MESSAGES` были ограничены на чат, но не по числу
  чатов. Добавлен потолок `MAX_TRACKED_CHATS`.

### Мелочи

- `emoji()` больше не падает `KeyError` на ключах `eye`/`like`, которых не было в
  fallback-словаре.
- Премиальные `<tg-emoji>` доступны только ботам с доп. именем, купленным на
  Fragment. Если Telegram отвергает разметку — выключается через `CUSTOM_EMOJI=0`.
- Дубли тем в `focus` больше не отмечаются пройденными разом (`tops.index()`
  возвращал первое совпадение).
- Очередь вопросов интервью строится по позиции, а не через `list.index()`.
- Кнопки викторины, опроса и задачи отвечают на callback сразу и не «залипают»
  спиннером до таймаута.
- Режим обучения не роняет викторину, если сессия не завелась.
- `.dockerignore` больше не тащит `progress.json` в образ, в `Dockerfile`
  добавлен `PYTHONUNBUFFERED=1` — иначе логи Railway приезжают пачками.

### Тесты

Добавлен `test_regressions.py` — офлайн, без ключей и обращений к API, закрывает
каждый пункт выше. Вместе с `test_interview_routing.py` это весь набор, который
можно гонять бесплатно; остальные `test_*.py` бьют по живому API.

## Известная проблема: токены в истории git

В ранних коммитах лежит `.env` с рабочим `TELEGRAM_BOT_TOKEN`, а в тестовых
скриптах — захардкоженный `NVIDIA_API_KEY`. Из рабочего дерева они убраны, но в
истории публичного репозитория остались, и их **нужно считать
скомпрометированными**: отозвать токен бота через `/revoke` у
[@BotFather](https://t.me/BotFather) и пересоздать ключ на
[build.nvidia.com](https://build.nvidia.com/). Переписывание истории само по себе
не помогает: GitHub держит недостижимые объекты, а форки и кэши могли их уже
подхватить.
